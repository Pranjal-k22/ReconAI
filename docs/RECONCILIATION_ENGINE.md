# ReconAI Deterministic Reconciliation Engine

## Purpose
The **ReconAI Deterministic Reconciliation Engine** is the core financial matching and anomaly classification system of ReconAI. It ingests normalized merchant orders, gateway payments, and bank settlement records to deterministically classify financial transactions, identify discrepancies, and calculate evidence-based confidence scores.

> [!IMPORTANT]
> **Zero LLM Participation in Primary Reconciliation**: Google Gemini does NOT participate in primary matching or anomaly classification. Reconciliation is 100% deterministic, reproducible, and executed locally in Node.js service modules.

---

## Input
The engine operates as a pure in-memory function taking plain objects:
- `merchantOrder`: Single `MerchantOrder` object (`merchantOrderId`, `amountPaise`, `currency`, `status`, `createdAtSource`, etc.).
- `gatewayPayments`: Array of zero or more `GatewayPayment` objects (`gatewayPaymentId`, `merchantOrderId`, `amountPaise`, `status`, `feePaise`, `taxPaise`, `refundAmountPaise`, etc.).
- `settlementRecords`: Array of zero or more `SettlementRecord` objects (`settlementRecordId`, `entityId`, `merchantOrderId`, `grossAmountPaise`, `feePaise`, `taxPaise`, `netAmountPaise`, `type`, etc.).

---

## Output
Returns a pure structured result object:
```javascript
{
  merchantOrderId: "ORD-000001",
  classification: "MATCHED", // or one of the 12 supported classifications
  confidence: 1.00,          // Deterministic score [0.00 - 1.00]
  gatewayPaymentIds: ["PAY-000001-A"],
  settlementRecordIds: ["SETREC-000001-A"],
  expectedAmountPaise: 149900,
  actualAmountPaise: 149900,
  differencePaise: 0,
  requiresReview: false,     // false for MATCHED, true for all anomalies
  reasons: ["Order, payment, and settlement successfully reconciled with zero discrepancies."],
  ruleEvidence: { ... }      // Machine-auditable structured evidence tree
}
```

> [!NOTE]
> Persistence identifiers (`resultId`, `runId`, `exceptionId`) are not generated by the pure engine; they are attached during database orchestration in subsequent steps.

---

## Evidence Hierarchy
Transactions are associated using a strict hierarchy of evidence:

1. **Strong Evidence**:
   - Direct `merchantOrderId` reference on `GatewayPayment` matching `MerchantOrder.merchantOrderId`.
   - Direct `entityId` reference on `SettlementRecord` matching `GatewayPayment.gatewayPaymentId`.
   - Direct `merchantOrderId` reference on `SettlementRecord`.

2. **Medium / Supporting Evidence**:
   - Financial amount equality (`amountPaise`).
   - Currency match (`INR`, `USD`).
   - Status compatibility (`PAID`, `CAPTURED`, `REFUNDED`).
   - Timestamp plausibility (order date $\le$ payment date $\le$ settlement date).

> [!WARNING]
> **Never Match Transactions by Amount Alone**: Two transactions having identical amounts (e.g. ₹1,499.00) without direct reference links or entity associations are NEVER matched automatically.

---

## Candidate Matching
- **Payment Candidates**: Identifies all gateway payments supplied for a given merchant order, calculating explicit boolean evidence (`directOrderReference`, `mismatchedOrderReference`, `amountMatches`, `currencyMatches`, `statusCompatible`, `timestampPlausible`).
- **Settlement Candidates**: Identifies bank settlement records linked to candidate payments via `entityId` or `merchantOrderId`.

---

## Classification Rules & Priority
The engine evaluates evidence in deterministic priority order:

1. **`INVALID_DATA`**: Schema-valid records containing reconciliation-invalid properties (e.g., currency conflict INR vs USD, or `UNKNOWN` status with missing linking keys).
2. **`MISSING_PAYMENT`**: Merchant order exists, but zero candidate gateway payments exist.
3. **`AMBIGUOUS`**: Multiple candidate payments exist with unlinked or inconclusive settlement evidence (e.g., `ORD-000116`), or multiple payments match without direct order references.
4. **`DUPLICATE_PAYMENT`**: Multiple captured gateway payments directly claim the same merchant order, with settlement linkage.
5. **`DUPLICATE_SETTLEMENT`**: Multiple settlement payout records exist for a single gateway payment.
6. **`REFERENCE_MISMATCH`**: Payment or settlement explicitly points to a conflicting order ID (e.g., `ORD-99000113` vs `ORD-000113`).
7. **`STATUS_MISMATCH`**: Incompatible execution status (e.g., Order is `PAID` while Gateway Payment is `FAILED`).
8. **`AMOUNT_MISMATCH`**: Gateway payment amount differs from merchant order amount.
9. **`REFUND_MISMATCH`**: Discrepancy between gateway refund amount and bank settlement refund payout.
10. **`FEE_MISMATCH`**: Settlement fee/tax or net payout differs from synthetic benchmark fee policy.
11. **`MISSING_SETTLEMENT`**: Captured gateway payment exists but lacks a bank settlement record.
12. **`MATCHED`**: Exact 3-way match across order, gateway payment, bank settlement, fee policy, net payout, and timestamps.

---

## Confidence Scoring
- Deterministic score between `0.00` and `1.00`.
- Represents **strength of evidence for the classification**.
- `MATCHED`: `1.00`.
- Deterministic anomalies (`AMOUNT_MISMATCH`, `MISSING_SETTLEMENT`, `MISSING_PAYMENT`, etc.): `0.95`.
- `AMBIGUOUS`: `0.45` (reflects high uncertainty requiring human review).

> [!NOTE]
> High confidence does NOT allow auto-reconciliation of anomalies. Any anomaly forces `requiresReview = true`.

---

## Synthetic Fee Policy
Exposed via pure module `server/src/services/finance/syntheticFeePolicy.js`:
- Standard synthetic gateway fee: **2% gross amount**.
- Standard tax on fee (GST): **18% of fee**.
- Net Payout: $\text{Gross} - \text{Fee} - \text{Tax}$.

---

## differencePaise Convention
Preserves the mandatory project convention:
$$\text{differencePaise} = \text{actualAmountPaise} - \text{expectedAmountPaise}$$

- Example: Expected ₹1,499.00 (149,900 paise), Actual ₹1,399.00 (139,900 paise) $\rightarrow$ `differencePaise = -10000`.
- For `MISSING_PAYMENT`, `actualAmountPaise = null` and `differencePaise = null`. Missing amounts are NEVER faked with `0`.

---

## GroundTruth Isolation
The engine operates in total isolation from GroundTruth:
- Production reconciliation services (`server/src/services/reconciliation/`) NEVER import `GroundTruth` or access expected answer fields.
- Verified by static architecture test: `server/tests/reconciliation/groundTruthIsolationGuard.test.js`.

---

## Failure-Safe Behavior
- Primary demo scenario `ORD-000116` with two ₹1,499 payment candidates and an unlinked settlement is classified as `AMBIGUOUS` with `requiresReview = true` and `confidence = 0.45`. The engine never guesses or auto-matches ambiguous records.

---

## Known Limitations
- V1 does not support foreign exchange (FX) currency conversions. Currency conflicts immediately produce `INVALID_DATA`.
